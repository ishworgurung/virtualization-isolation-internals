## The idea

"Lock-free" = threads coordinate with atomic instructions instead of mutexes, so
one stalled thread cannot block the others. The simplest and most useful form
needs **no CAS at all**: a ring where each index has a single writer.

```
 slots: [ . . X X X X . . ]     producer writes only `tail`
              ^       ^         consumer writes only `head`
            head     tail       fill = tail.wrapping_sub(head)   (free-running counters)
```

**This is the same structure** as the virtio virtqueue (`01-virtio/`: avail ring
guest→host, used ring host→guest) and io_uring's SQ/CQ (`04-io_uring/`: you produce
SQEs, kernel produces CQEs). Understand this ring and you understand all three.

## Pitfall 1 — memory ordering

```
producer:  write slot;             tail.store(n, Release)
consumer:  tail.load(Acquire);     read slot
```

Release "publishes" everything written before it; an Acquire that observes the
value sees all of it. Drop the pair to `Relaxed` and the consumer may observe
the new `tail` yet read stale slot bytes.

`litmus.rs` tests exactly that. **Honest result on this machine (x86-64):
0 stale reads in both configurations** — x86's TSO memory model never reorders
store→store or load→load in hardware, so the bug is invisible there even though
it is real (the compiler may reorder Relaxed accesses; ARM/POWER/RISC-V CPUs do).
Run it on an AArch64 box to watch Relaxed fail, or use a model checker (`loom`)
on x86. Don't trust "it passed on my laptop" for lock-free code.

## Pitfall 2 — ABA

CAS checks *value*, not *history*. If `head` goes A → B → A during your pop, your
CAS succeeds against a world that no longer exists. `aba_demo` replays it
deterministically by running a closure between the read and the CAS:

```
--- UNTAGGED ---
T1 read head=A, next=B ... paused
T2 popped A then B; is now using B elsewhere; pushed A back: A -> C
T1's CAS SUCCEEDED and returned A.   stack now: B
=> CORRUPTION: node C is lost, B is both 'in use by T2' and on the stack.

--- TAGGED (index + generation) ---
T1's CAS FAILED (generation changed), so T1 would retry.   stack still: A -> C
```

Fixes: **tagged/versioned pointers** (shown; costs a double-width CAS or packing
bits), **hazard pointers**, **epoch-based reclamation** (crossbeam-epoch), or
avoiding node reuse. Note that with raw pointers + `free()` this is also a
use-after-free; the arena version here isolates the logic bug. (Rust does not
save you: this is a *logic* race, not a data race.)

## Pitfall 3 — false sharing

Cores exchange memory in 64-byte cache lines. Two threads writing *different*
variables on the *same* line make it ping-pong between their caches.
`false_sharing.rs`, this machine:

```
2 threads x 500000000 increments of their OWN counter:

                                     ms    ns/op   ops/ns
  adjacent (false sharing)       7984.4    15.97    0.125
  padded (separate lines)        1740.6     3.48    0.575

  slowdown from false sharing: 4.6x
```

`ns/op` is the latency of one increment seen by one thread; `ops/ns` is both
threads' combined throughput. Padded, an increment is an uncontended
`lock add` (~3.5 ns); adjacent, each one also waits for the line to come back
from the other core (~16 ns).

The SPSC ring pads `head` and `tail` for this reason, and caches the remote
index so each side touches the other's line only when the ring looks full/empty.

## Benchmark — and what it means in practice

```
Mutex<VecDeque> (spinning)     1048.4 ms         9.5 M items/s
std::sync::mpsc (bounded)       119.3 ms        83.8 M items/s
lock-free SPSC ring              94.1 ms       106.2 M items/s
```

Read it carefully:

* A naive mutex queue is ~11× slower — contention on one lock word. (An
  earlier version of this benchmark had a bug that made it 1–30 s at random;
  next section.)
* But **the standard library channel is already within 1.3× of the hand-written
  ring**, because it is itself lock-free inside. The hand-rolled structure buys
  ~25% here, not an order of magnitude.
* So the honest rule: **use the standard/library primitive; write your own only
  on a profiled hot path** where you know the topology (exactly one producer and
  one consumer) and need the last bit — e.g. a vCPU-thread ↔ device-thread queue
  or a per-core log buffer. Lock-free code is expensive to get right and to
  review; a bug is a silent data corruption, not a crash.

### Bug story: why the mutex time jumped around (1 s one run, 30 s the next)

An earlier version of `spsc_bench` gave wildly different mutex times on the
same machine, while the other two stayed steady:

```
Mutex<VecDeque> (spinning)     2985.2 ms        3.3 M items/s
Mutex<VecDeque> (spinning)     9216.5 ms        1.1 M items/s
std::sync::mpsc (bounded)  ~109 ms both runs
lock-free SPSC ring        96–109 ms both runs
```

**Wrong guess 1: core placement.** This i9-12900K mixes fast P-cores and slow
E-cores, so maybe each run got different cores. Pinning with `taskset` did not
fix it — the same two P-cores gave 6433 ms and then 1145 ms:

| CPUs (`taskset -c`) | Run 1 | Run 2 |
|---|---|---|
| 0,2 — two P-cores | 6433 ms | 1145 ms |
| 16,17 — two E-cores, same cluster | 1758 ms | 1334 ms |
| 16,20 — two E-cores, different clusters | 4460 ms | 19181 ms |
| 0,16 — one P-core, one E-core | 1667 ms | 1721 ms |

**Wrong guess 2: threads sleeping in the kernel.** When `std::sync::Mutex` is
contended it can put a thread to sleep (`futex`), and waking it is slow. But
`perf stat -e context-switches` showed a few hundred switches in a 1 s run
*and* in a 31 s run. Nobody was sleeping; both threads were busy the whole time.

**Measuring what they were busy with.** A copy of the loop with counters
(lock acquisitions, "queue full" retries, "queue empty" polls):

```
   886 ms  consumer: locks  11.0M  empty-polls   1.0M
  1378 ms  consumer: locks  13.2M  empty-polls   3.2M
  5743 ms  consumer: locks  72.6M  empty-polls  62.6M
 21136 ms  consumer: locks 269.5M  empty-polls 259.5M
 24245 ms  consumer: locks 315.2M  empty-polls 305.2M
```

The time tracks the number of times the consumer found the queue **empty**.
The producer (10 M pushes, ~0 "full" retries) was being shut out.

**The cause — one line of Rust:**

```rust
if let Some(v) = q.lock().unwrap().pop_front() {
    ...
} else {
    std::hint::spin_loop(); // still holding the lock here!
}
```

`q.lock()` returns a guard, a temporary value that unlocks when it is dropped.
In Rust 2021, a temporary in an `if let` condition lives until the end of the
**whole `if let ... else`**. So when the queue was empty, the consumer spun
*while holding the lock*, unlocked, looped, and locked again. Two more facts
turn that into a trap:

1. **`std::sync::Mutex` is not fair.** It does not serve waiters in order. The
   thread that just unlocked usually wins the next lock too: the lock's cache
   line is still in its core, while the other thread must fetch it from
   another core.
2. **It feeds itself.** Empty queue → consumer keeps the lock → producer can't
   push → queue stays empty. Timing noise early in the run decides whether it
   falls into this loop, and for how long. That is why the times jump between
   values instead of spreading evenly around an average.

**The fix** takes the item in its own statement, so the guard is dropped at
the `;` before any spinning:

```rust
let item = q.lock().unwrap().pop_front(); // lock released here
if let Some(v) = item { ... } else { std::hint::spin_loop(); }
```

After the fix, 15 runs (10 pinned, 5 unpinned): 857–1127 ms, every time.
(Edition 2024 changed this rule: `if let` temporaries are dropped before the
`else` runs. This crate is edition 2021.)

Lessons:

* **Hold a lock only for the critical section**, and know where Rust drops the
  guard. `let x = m.lock().unwrap().thing();` drops it at the `;`; a guard
  used in an `if let`/`match` condition can live much longer.
* **Unfair locks + busy-waiting can starve a thread** for billions of cycles
  without a single context switch.
* **Run a benchmark more than once and look at the spread.** A 30× spread is
  a bug signal, not noise. Then measure instead of guessing: both first guesses
  here sounded plausible and both were wrong.

## Interesting bits (not really about lock-free)

Things that came up while pinning threads for the benchmark above, worth
knowing even outside this lab.

### `taskset` and P-cores vs E-cores

This i9-12900K mixes fast P-cores and slow E-cores, and the scheduler is free
to put a thread on either. There's no knob that says "P-cores only" globally;
you restrict *which* CPUs a thread may run on:

* **One command:** `taskset -c 0,2,8,10,12,14 cargo run --release --bin spsc_bench`
  (that CPU list is this machine's P-cores; 4 and 6 are isolated for other
  work, and SMT is off so their odd-numbered siblings aren't online). Every
  thread the process spawns inherits the mask. A program can also set its own
  mask with `sched_setaffinity` (the `core_affinity` crate in Rust).
* **Everything by default:** `CPUAffinity=0 2 8 10 12 14` in
  `/etc/systemd/system.conf`, then reboot — every service and login session
  starts confined to those CPUs, and children inherit it.
* **Turn E-cores off entirely:** in the BIOS (OC → Advanced CPU Configuration
  → Active E-Cores = 0). Simplest, but gives up 8 cores of parallelism.

Caution from this lab: pinning to P-cores made results *repeatable*, but it
did not fix the wild mutex variance above — that was a real bug (the lock
staying held while spinning), not a scheduling artifact. Pin cores to remove
one source of noise, but don't stop measuring once you have.

### Does this matter on cloud VMs?

Not really — P/E hybrid cores are a desktop/laptop/mobile thing. Cloud
instances, bare metal included, don't run client chips like this i9-12900K;
they use server-grade CPUs with **homogeneous** cores:

* **Intel:** Xeon Scalable (Ice Lake, Sapphire Rapids, and newer). Intel's
  hybrid designs (Alder Lake, Raptor Lake, Meteor Lake, Lunar Lake) are
  client-only — the server line has stayed single-core-type.
* **AMD:** EPYC (Genoa, Bergamo, ...). AMD's "big vs small core" choice is
  *which part* the machine uses (Genoa = fewer big cores, Bergamo = more,
  denser Zen4c cores) — never both types mixed in one machine.
* **Arm servers:** homogeneous Neoverse cores, no big.LITTLE split.

So the `taskset -c <P-cores>` / `CPUAffinity=` / BIOS-E-core-off advice above
has nothing to apply to there — there's no slow core type to steer away from.
The closest analogous problems on server hardware are:

* **NUMA locality on multi-socket machines** — pinning across NUMA nodes has
  the same "wrong placement = slow and inconsistent" flavor as the P/E case,
  but the axis is memory distance, not core speed. `numactl --cpubind
  --membind` is the rough equivalent of `taskset` there.
* **SMT siblings on small VMs** — a 2-vCPU VM's vCPUs are typically the two
  SMT (hyperthread) siblings of one physical core, so pinning two hot,
  independent threads there recreates the contention feel of this lab's
  false-sharing/mutex sections even with no P/E split at all.
* **Disabling SMT without BIOS access:** many providers offer a
  threads-per-core = 1 option at VM creation, the closest analog to "disable
  SMT in the BIOS" when you don't own the hardware.

**Same problem, three scales.** Older multi-socket servers needed
`processor.max_cstate=1`-style tuning because C3/C6 exit latency showed up as
jitter across QPI-connected sockets — the same idle-state-vs-latency trade-off
as `intel_idle.max_cstate` in [the tuning guide](../optimizing-linux-for-ultra-performance.md#4-frequency-and-sleep-states)
on this single-socket desktop. What NUMA pinning (`numactl --cpubind
--membind`) defends against on multi-socket machines is a step further: not
just "wrong core" but "wrong *socket*, with its own local RAM," paid as real
cross-interconnect latency on every remote memory access. Same underlying
problem (an idle or distant resource costs more to reach than it looks like
it should), at different scales: cores on one die, sockets on one board.

### `taskset` inside containers

`taskset` still works in a container, but what it can select depends on
*how* the container was given CPUs:

* **`--cpus=5` (a quota, the `cpu` cgroup controller):** throttles total
  CPU-seconds per second: it does **not** restrict which CPUs are usable.
  `taskset -c` inside the container can still pick any host CPU that was
  visible to it before the quota was applied.
* **`--cpuset-cpus=0,2,4,6,8` (an affinity mask, the `cpuset` cgroup
  controller):** this is the container equivalent of `sched_setaffinity` —
  Docker/Podman/Kubernetes implement it by writing to `cpuset.cpus` in the
  container's cgroup. Now `taskset -c` inside the container can only choose a
  *subset* of that list; asking for a CPU outside it fails with `EINVAL`, and
  `nproc`/`sched_getaffinity()` report only those CPUs.

Check what a running container actually has:

```sh
cat /sys/fs/cgroup/cpuset.cpus.effective        # from inside the container (cgroup v2)
docker inspect --format '{{.HostConfig.CpusetCpus}}' <container>
```

So to confine a containerized workload to P-cores only, use
`--cpuset-cpus=0,2,8,10,12,14` at container-create time — `--cpus=5` alone
does not guarantee P-core-only placement, just less total time on whichever
cores the scheduler picks.

## The same ideas in Go

* `sync/atomic` (`atomic.Int64`, `atomic.Pointer[T]`, `atomic.Value`) gives
  sequentially-consistent atomics; Go's memory model says atomics are
  synchronising, so there is no Relaxed/Acquire/Release dial to get wrong (and
  none to tune).
* `atomic.Pointer[T]` + copy-on-write is the idiomatic lock-free read path for
  config/routing tables: readers `Load()`, writers build a new value and
  `Store()`/`CompareAndSwap()`. Go's GC removes the ABA-via-free problem for
  pointers (a node cannot be recycled while reachable), which is a real advantage.
* For a Go SPSC queue, a buffered channel is normally the answer; benchmark before
  replacing it.
* False sharing exists in Go too: pad hot per-CPU counters (`_ [64]byte`, or
  `cpu.CacheLinePad` from `golang.org/x/sys/cpu`).

## In short

Lock-free means atomics instead of locks. The workhorse is the SPSC ring —
one writer per index, acquire/release to publish — which is exactly what
virtqueues and io_uring are. The traps are memory ordering, ABA and false
sharing, and in Go channels or a mutex come first, with lock-free reserved for a
profiled hot path.
