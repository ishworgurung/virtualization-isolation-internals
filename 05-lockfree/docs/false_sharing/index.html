False sharing, measured.

Two threads each hammer THEIR OWN counter. Logically there is zero sharing. Case 1 places the counters adjacent (same 64-byte cache line); case 2 pads them onto separate lines. Same work, same instructions, different speed.

§What is a cache line?

The unit of memory a CPU moves between RAM and its caches: 64 bytes on x86-64 and most ARM (128 on Apple M-series). Check yours with getconf LEVEL1_DCACHE_LINESIZE.

RAM is slow (~100 ns per access), so each core keeps copies of recently used memory in small, fast caches (L1 ~1 ns, then L2, L3). Caches never hold individual variables, only whole 64-byte blocks. The line is the unit of transfer, not the size of your data: reading a 1-byte u8 still fetches the whole 64-byte block of memory it sits in, i.e. your byte plus its 63 neighbouring bytes (other variables, array elements, struct fields), on the bet that nearby data will be needed soon:

  line at 0x1000 (64 bytes):
  [ neighbours ... | your u8 at 0x1008 | ... more neighbours ]

So a line holds whatever happens to be in that 64-byte block, and any two variables in the same block share a line.

Which line an address lives on: divide by 64 (same as addr >> 6):

  0x1000..0x103F            -> line 0x40
  0x1040..0x107F            -> line 0x41
  a at 0x1008, b at 0x1010  -> both on line 0x40

That is what the line closure in main computes.

§Why case 1 is slow

A core may write a line only while it holds the only copy (cache coherence, the MESI protocol). Before writing, it invalidates every other core’s copy. With a and b (8 bytes each) on the same line:

  1. Core 0 increments a -> the line is invalidated in core 1’s cache.
  2. Core 1 increments b -> it must fetch the line back (tens of ns), invalidating core 0’s copy.
  3. Repeat ITERS times.

Each thread only touches its own counter, but the hardware tracks ownership per line, not per variable, so the line ping-pongs between the cores. That is false sharing: nothing is logically shared, yet the cores behave as if it were. CachePadded gives each counter its own 64-byte line, so each core keeps its line in L1 and never waits for the other (~4x faster on the machine in the README). More background and diagrams: src/padded.rs.
