Message-passing litmus test: why acquire/release exist.

A “litmus test” is a tiny concurrent program whose possible outcomes reveal what a memory model allows. This is the most important one:

Writer: data = 1; flag = 1; Reader: wait until flag == 1; then read data. Must it see data == 1?

Intuition says “obviously yes: data was written first”. But “first” only holds inside the writer thread. The CPU may make the two stores visible to other cores in a different order (e.g. data still sits in the writer’s store buffer when flag reaches memory), and the compiler may swap two stores that look independent to it. The orderings are how you forbid that:

flag stored Release / loaded Acquire -> YES, guaranteed by the language. flag stored Relaxed / loaded Relaxed -> NO guarantee. The reader may see flag == 1 and stale data == 0.

HONEST CAVEAT: x86-64 has Total Store Order — the hardware never reorders two stores or two loads — so on x86 you will almost certainly see 0 violations even for Relaxed. The bug is still real: (a) the compiler may reorder Relaxed accesses, and (b) on ARM/POWER/RISC-V the CPU does. Run this on an AArch64 machine (e.g. an Arm cloud server) to see Relaxed fail; to check algorithms without such hardware use a model checker like loom. (The one reordering x86 does perform is a store followed by a load of a different address; that is what SeqCst fences exist for.)

Run: cargo run –release –bin litmus
