The ABA problem, made reproducible.

§Refresher: stack, linked list, arena

A stack is LIFO (last in, first out), like a pile of plates: push puts an item on top, pop takes the top one off.

A singly linked list stores each item in a node that also holds a link (“next”) to the node below it. The list itself is just a pointer to the top node, called head. The bottom node’s next is a special “nothing” value (NIL here, null in C):

  head ──▶ [A | next] ──▶ [B | next] ──▶ [C | next = NIL]
  top of stack                            bottom of stack
  • push(X): set X.next = head, then head = X.
  • pop(): remember top = head, then head = top.next, return top.

Both are O(1) and only ever change one shared variable, head. That is what makes a lock-free version possible.

An arena is a fixed array (Vec<Node>) that owns all the nodes. Instead of pointers we use indices into it: “node 2” means nodes[2]. Nothing is ever allocated or freed, which keeps the demo memory-safe.

§Refresher: the CAS retry loop

With several threads, “read head, then write head” is broken: another thread may change head in between, and our write would erase its work. The lock-free pattern is:

  loop {
      old = head.load()                 // 1. look
      new = compute from old            // 2. prepare, privately
      if CAS(head, old, new) succeeds:  // 3. "if head is STILL old, set it to new"
          done
      // else someone changed head since step 1: start over with fresh data
  }

A Treiber stack (R. K. Treiber, 1986) is exactly that loop applied to a linked-list stack.

§The bug

CAS checks the value, not the history. If X goes A → B → A between your read and your CAS, the CAS succeeds — but the world it was justified by no longer exists.

  pop():  old = head            // A
          next = old.next       // B          <-- decided based on THIS
          ...another thread runs here...
          CAS(head, old, next)  // "head is still A? then head = B"

If, meanwhile, another thread pops A, pops B, and pushes A back, head is A again and the CAS succeeds — installing B, a node that is no longer in the stack. Node C is lost, B is double-owned. Step by step:

  start:                 head ─▶ A ─▶ B ─▶ C
  T1 reads:              old = A, next = B       ... T1 pauses
  T2 pops A:             head ─▶ B ─▶ C
  T2 pops B:             head ─▶ C               (T2 now owns B, reuses it:
                                                  B.next = NIL)
  T2 pushes A:           head ─▶ A ─▶ C
  T1 resumes: CAS(head, A, B): head IS A, so it succeeds!
  result:                head ─▶ B ─▶ NIL        C is lost, B belongs to T2

With raw pointers this is also a use-after-free (B’s memory may be freed and reused). Here we use an index-based arena, so it is a pure logic error, but the mechanics are identical and — unlike the real thing — perfectly deterministic: TreiberStack::pop_with_hook runs a closure between the read and the CAS so a “second thread” can be injected at exactly that point. Rust’s type system does not catch this: every access is a well-defined atomic operation, so there is no data race, only a wrong algorithm.

§The fix: tagged (versioned) heads

Pack a generation counter next to the index and bump it on every successful CAS. Then A→B→A is really (A,1)→(B,2)→(A,3); the stale CAS expects (A,1) and fails. Other cures: hazard pointers, epoch-based reclamation (crossbeam), or never reusing nodes while readers may hold them. (A 32-bit tag can in principle wrap around after 2^32 successful operations during one stalled pop; in practice that window is considered negligible. With real 64-bit pointers there is no room for a tag in one word, so implementations either steal unused pointer bits or use a double-width CAS such as x86-64’s cmpxchg16b.)

Why pack both into ONE u64 instead of two separate atomics? CAS compares and swaps one memory word. Index and tag must be checked together, in a single indivisible step; two separate CASes would reopen a gap in between.
