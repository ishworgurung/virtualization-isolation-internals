A bounded, wait-free single-producer / single-consumer ring buffer.

This is the data structure behind virtio virtqueues, io_uring’s SQ/CQ and most audio/network fast paths.

§What problem it solves

One thread (the producer) creates items; another (the consumer) processes them, in the same order (FIFO: first in, first out). They run at different speeds, so we need a waiting room between them: a queue. “Bounded” means the queue has a fixed maximum size; when it is full, push fails instead of allocating more memory. “Single-producer/single-consumer” (SPSC) means exactly one thread pushes and exactly one thread pops.

§Refresher: the ring buffer (circular buffer)

A queue stored in a fixed array. Two positions: head (where the next item will be read) and tail (where the next item will be written). Push writes at tail and moves tail forward; pop reads at head and moves head forward. When a position reaches the end of the array, it wraps to slot 0 — the array is used as if it were a circle:

  capacity 8, after pushing 1..=6 and popping 1..=2:

  slot:   0   1   2   3   4   5   6   7
        [ .   .   3   4   5   6   .   . ]
                  ^               ^
                 head=2          tail=6          fill = 6 - 2 = 4

  push 7, 8, 9: tail passes the end and wraps to slot 0

  slot:   0   1   2   3   4   5   6   7
        [ 9   .   3   4   5   6   7   8 ]
              ^   ^
         tail=9  head=2      (tail as a counter is 9; its slot is 9 % 8 = 1)

Nothing is ever shifted or copied around; only the two positions move. Both push and pop are O(1).

§Why this needs no lock and no CAS

Each index has exactly one writer:

  slots:   [ . . X X X X . . ]
                 ^       ^
               head      tail
        consumer writes   producer writes
        (pop advances)    (push advances)
  • tail — next slot the producer will fill. Only the producer stores it.
  • head — next slot the consumer will read. Only the consumer stores it.

Each side only reads the other side’s index, to learn how far it may go. Two threads never race to write the same variable, so plain atomic loads and stores are enough; no compare-and-swap is needed.

§Free-running counters, masks and wrap-around

head and tail are free-running usize counters: they count every item ever pushed/popped and are never reduced mod capacity. The actual slot is counter & mask, where mask = capacity - 1 (capacity is a power of two; see the bits refresher in lib.rs):

  capacity 8 -> mask 7 = 0b0111
  counter 13 = 0b1101;  13 & 0b0111 = 0b0101 = 5   (same as 13 % 8)
  • fill level = tail.wrapping_sub(head)
  • empty ⇔ tail == head
  • full ⇔ tail - head == capacity

This removes the classic “keep one slot empty to tell full from empty” trick: if you stored slot numbers (0..cap) instead of counters, an empty ring and a full ring would both have head == tail.

Why wrapping_sub is still right after the counter overflows. A usize counter wraps back to 0 after 2^64 increments (at a billion pushes a second, that takes ~584 years, but correctness should not depend on that). The same thing, shrunk to a u8 so the numbers are readable (u8 wraps at 256):

  head = 254, then 3 pushes: tail = 254 + 3 = 257 -> wraps to 1
  tail - head = 1 - 254 = -253 -> as u8 (mod 256): 256 - 253 = 3   correct!

Subtraction mod 2^N gives the right distance as long as the true distance is below 2^N, which it always is (it is at most the capacity).

§Memory ordering — the whole game

Modern CPUs and compilers reorder memory accesses whenever a single thread cannot tell the difference. Another thread can. Orderings tell both what must not be reordered:

Push: write the slot, then tail.store(.., Release). Pop: tail.load(Acquire), then read the slot.

Analogy: the producer puts a parcel in a locker (writes the slot), then raises a flag (stores tail). The consumer waits for the flag, then opens the locker. Without ordering, the flag could be raised before the parcel is in the locker, and the consumer would find it empty.

The Release store “publishes” every write that came before it in program order (the slot contents). The Acquire load that observes the new tail synchronises-with it, guaranteeing the slot contents are visible. With Relaxed on both sides the consumer could see the new tail but stale slot bytes — on ARM/POWER for real, on x86 only via compiler reordering.

The symmetric edge protects the reuse of a slot: the consumer finishes reading, then head.store(.., Release); the producer’s head.load(Acquire) guarantees it will not overwrite a slot still being read.

  producer                              consumer
  --------                              --------
  buf[t & mask] = value
  tail.store(t+1, Release)  ─────────▶  tail.load(Acquire) sees t+1
                                        value = buf[h & mask]
  head.load(Acquire) sees h+1  ◀──────  head.store(h+1, Release)
  (now slot h may be overwritten)

On x86-64 an Acquire load and a Release store compile to ordinary mov instructions (the hardware already provides that ordering); they only stop the compiler from reordering. On ARM64 they become ldar/stlr.

§Two performance details

  1. Cache-line padding of head and tail (see crate::padded): they are written by different cores, so sharing a line would false-share.
  2. Cached remote index. Loading the other side’s index pulls its cache line across cores. Each side keeps a private copy and only re-reads the real one when the ring looks full/empty. Under steady load this cuts cross-core traffic to about one line transfer per batch instead of per item.

§Rust types used here, briefly

  • Arc<T> — a reference-counted pointer that can be shared between threads. Producer and Consumer each hold one; the Shared state is freed when the last of them is dropped.
  • Box<[T]> — a fixed-size heap array (like Vec<T> without the ability to grow).
  • UnsafeCell<T> — the only legal way in Rust to mutate something through a shared reference &. Normally & means “read-only”; UnsafeCell opts out and makes you responsible for preventing data races.
  • MaybeUninit<T> — room for a T that may or may not currently hold a value. Rust never reads or drops it on its own; we track which slots are full (the ones in [head, tail)).
  • unsafe { .. } — “compiler, I have checked the rules you can’t check”. Every unsafe block below has a SAFETY: comment saying why it holds.
  • Result<(), T> / Option<T> — Rust’s way to return “success or failure” and “a value or nothing” without exceptions or null.
