The naive approach: one lock around a double-ended queue. Every push and pop contends on the same mutex (and the same cache line).

A bug that used to live here: the consumer spun while holding the lock. Its time jumped between ~1 s and 30+ s from run to run, even pinned to the same two P-cores. How it happened:

  • The guard from if let Some(v) = q.lock().unwrap().pop_front() lives until the end of the whole if let ... else (edition 2021), so the “queue empty → spin_loop()” branch ran with the lock held.
  • std::sync::Mutex is not fair: the thread that just unlocked usually wins the next lock too, because the lock’s cache line is still in its core. So an empty-queue consumer could unlock and relock hundreds of millions of times while the producer rarely got in — and without the producer getting in, the queue stayed empty. A self-sustaining loop.
  • Whether a run fell into that loop depended on timing noise early on. Instrumented: fast runs had ~1–10 M empty polls; slow ones 60–300 M. Context switches were a few hundred either way — nobody slept; the time was all lock traffic.

Now the item is taken in its own statement, so the lock is released before spinning. The lessons: hold a lock only for the critical section, and watch where Rust drops temporaries. See the README section “Why the mutex time jumped around” for the measurements.
