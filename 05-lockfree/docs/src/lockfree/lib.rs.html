1//! # lockfree
2//!
3//! Small, heavily-commented lock-free building blocks:
4//!
5//! * [`spsc`]   — bounded single-producer/single-consumer ring (acquire/release,
6//!                cached indices, cache-line padding). Same shape as a virtqueue
7//!                or an io_uring ring.
8//! * [`aba`]    — a Treiber stack that makes the ABA problem reproducible on demand,
9//!                and the tagged-pointer fix.
10//! * [`padded`] — `CachePadded<T>`, the cure for false sharing.
11//!
12//! The binaries in `src/bin/` exercise each one:
13//! `spsc_bench`, `aba_demo`, `false_sharing`, `litmus`.
14//!
15//! ## Suggested reading order
16//!
17//! 1. This file: vocabulary + the bits refresher below.
18//! 2. `padded.rs` (short) — what a cache line is.
19//! 3. `spsc.rs` — the ring buffer. The most important file.
20//! 4. `bin/litmus.rs` — why the orderings in `spsc.rs` matter.
21//! 5. `aba.rs` + `bin/aba_demo.rs` — what goes wrong once you need CAS.
22//! 6. `bin/false_sharing.rs`, `bin/spsc_bench.rs` — measure it.
23//!
24//! ## Vocabulary used throughout
25//!
26//! * **Thread**: an independent flow of execution. Two threads may run at the
27//!   *same instant* on two CPU cores, or take turns on one core. Either way, you
28//!   cannot predict where one thread is when another looks at shared memory.
29//! * **Lock / mutex**: the classic way to share data: "only one thread may be in
30//!   here at a time". Simple and correct, but a thread that is paused while
31//!   holding the lock (descheduled, page-faulting) stalls everyone waiting on it.
32//! * **Lock-free**: threads coordinate through atomic instructions instead of
33//!   mutexes, and the system as a whole always makes progress — a thread that
34//!   is paused can never block the others.
35//! * **Wait-free** (stronger): *every* operation finishes in a bounded number of
36//!   its own steps, no matter what other threads do. The SPSC ring is wait-free;
37//!   the Treiber stack is only lock-free (a CAS may have to retry).
38//! * **Atomic**: a memory access the CPU performs indivisibly (no torn reads or
39//!   writes — you never see half of an old value and half of a new one) and that
40//!   the compiler may not split, merge or elide. In Rust: `AtomicUsize`,
41//!   `AtomicU32`, `AtomicU64`, ... with methods `load`, `store`, `fetch_add`,
42//!   `compare_exchange`. (The word means other things in databases and
43//!   distributed systems; see [Atomicity in other
44//!   contexts](#atomicity-in-other-contexts).)
45//! * **Memory ordering** (`Relaxed`, `Acquire`, `Release`, `AcqRel`, `SeqCst`):
46//!   rules about which *other* memory accesses become visible to another thread
47//!   together with an atomic one. See `spsc.rs` and the `litmus` binary.
48//!   - `Relaxed`: "just make this one access atomic; no promises about others".
49//!   - `Release` (on a store): "everything I wrote before this is published too".
50//!   - `Acquire` (on a load): "if I see a Released value, I also see everything
51//!     written before it".
52//!   - `AcqRel`: both, for read-modify-write operations such as CAS.
53//!   - `SeqCst`: Acquire/Release plus one global order all threads agree on.
54//! * **CAS** (compare-and-swap, `compare_exchange` in Rust): "if X still equals
55//!   OLD, set it to NEW; tell me whether it worked" — the basic lock-free
56//!   read-modify-write building block. It is ONE hardware instruction
57//!   (`lock cmpxchg` on x86), so no other thread can sneak in between the
58//!   compare and the swap.
59//! * **Happens-before**: if A happens-before B, then B sees A's effects.
60//!   Within one thread, program order gives you this for free. Across threads,
61//!   you only get it through a synchronising pair such as Release → Acquire.
62//!
63//! ## Atomicity in other contexts
64//!
65//! "Atomic" is an overloaded word. The common core is always **no observer
66//! ever sees a half-done state**; what changes is *who* the observer is and
67//! *what* could interrupt the operation halfway.
68//!
69//! | Context | "Atomic" means | Protects against | Scope |
70//! |---|---|---|---|
71//! | **CPU / Rust atomics** (this crate) | a single memory access is indivisible; no torn values | other threads running at the same time | one memory location, a few bytes |
72//! | **Databases** (the A in ACID) | a transaction's writes happen all-or-nothing | a **crash** mid-transaction | many rows, one database |
73//! | **Distributed atomic commit** (two-phase commit, 2PC) | every node commits, or every node aborts | node crashes, lost messages | many machines |
74//! | **Atomic broadcast** (a.k.a. total-order broadcast) | every node delivers the same messages in the same order | nodes seeing events in different orders | many machines; equivalent to consensus (Raft, Paxos) |
75//! | **Filesystems** ("atomic rename") | readers see the old file or the new one, never a partial one | crash during a write, concurrent readers | one path |
76//!
77//! **Trap: atomic is not isolated.** ACID atomicity is about *crashes*, not
78//! concurrency; concurrency is the **I** (isolation). An "atomic" transaction
79//! can still suffer race anomalies, just as a Rust atomic does not order your
80//! *other* memory accesses (that is what `Acquire`/`Release` add). In both
81//! worlds atomicity is the weaker guarantee, and ordering/isolation is a
82//! separate one you must ask for.
83//!
84//! **Where the worlds meet: linearizability.** Distributed-systems theory has
85//! the *atomic register* (Lamport): a shared variable whose every read and
86//! write appears to take effect at a single instant somewhere between its call
87//! and its return. That property is **linearizability**, which Jepsen calls
88//! *atomic consistency*. Operations on a single CPU atomic are linearizable,
89//! so an `AtomicU64` is effectively the one-machine, nanosecond-scale version
90//! of what etcd or ZooKeeper provide across a cluster in milliseconds. The
91//! ring in [`spsc`] and a Raft log are the same idea at very different scales.
92//!
93//! In one line: on a CPU, "atomic" = indivisible for other threads; in a
94//! database, all-or-nothing across a crash; across a cluster, all nodes agree,
95//! which needs consensus.
96//!
97//! ## Refresher: bits, hex, shifts and masks
98//!
99//! Lock-free code uses a handful of bit tricks. Here they are with numbers.
100//!
101//! **Binary and hex.** A `u8` has 8 bits; `0b0000_1101` is 13. Hex groups four
102//! bits per digit: `0xD` = `0b1101` = 13, `0xFF` = `0b1111_1111` = 255.
103//! `u32::MAX` is `0xFFFF_FFFF` (32 ones). Underscores are only for readability.
104//!
105//! **AND `&`** keeps a bit only if it is 1 in *both* inputs. Used to *extract*
106//! or *test* bits:
107//!
108//! ```text
109//!     13 = 0b1101
110//!   &  7 = 0b0111
111//!   -------------
112//!      5 = 0b0101      (the top bit was "masked off")
113//! ```
114//!
115//! **OR `|`** sets a bit if it is 1 in *either* input. Used to *combine* fields
116//! that occupy different bits:
117//!
118//! ```text
119//!     0b1100_0000
120//!   | 0b0000_0011
121//!   -------------
122//!     0b1100_0011      (neither side overwrote the other)
123//! ```
124//!
125//! **Left shift `<<`** moves bits towards the high end, filling with zeros.
126//! `x << n` equals `x * 2^n` (as long as nothing falls off the top):
127//! `1 << 3 = 0b1000 = 8`, `5 << 32 = 0x0000_0005_0000_0000`.
128//!
129//! **Right shift `>>`** moves bits towards the low end; the low bits fall off.
130//! `x >> n` equals `x / 2^n` rounded down: `13 >> 2 = 3`, and
131//! `0x0000_0005_0000_0002 >> 32 = 5`.
132//!
133//! **Casting to a narrower type truncates**: `0x0000_0005_0000_0002_u64 as u32`
134//! keeps only the low 32 bits → `2`. Casting to a wider type zero-extends.
135//!
136//! **Powers of two and masks.** If `cap` is a power of two (2, 4, 8, 16...),
137//! then `mask = cap - 1` is all ones below it (`8 - 1 = 7 = 0b0111`), and
138//! `i & mask == i % cap` for every `i`. `%` (division) costs tens of cycles;
139//! `&` costs one. That is why ring buffers insist on power-of-two sizes. It only
140//! works for powers of two: `cap = 6` gives `mask = 5 = 0b101`, and `2 & 5 = 0`,
141//! not `2`.
142//!
143//! **Wrapping arithmetic.** Integers have a fixed number of bits, so they wrap:
144//! for `u8`, `255 + 1` → `0` and `0 - 1` → `255` (arithmetic mod 256). In
145//! debug builds Rust panics on overflow, so code that *wants* wrapping says so:
146//! `wrapping_add`, `wrapping_sub`. The useful property: `b.wrapping_sub(a)`
147//! is still the true distance from `a` to `b` even if `b` has wrapped past zero
148//! (see `spsc.rs` for a worked example).
149//!
150//! ### Unsigned vs signed integers
151//!
152//! **The one idea.** A number type is a fixed number of bits, so it has a fixed
153//! number of *bit patterns*. 8 bits give 256 patterns, from `0000_0000` to
154//! `1111_1111`. The type only decides **which number each pattern means**:
155//!
156//! * unsigned (`u8`): the patterns mean 0, 1, 2, ..., 255
157//! * signed (`i8`): the patterns mean -128, ..., -1, 0, 1, ..., 127
158//!
159//! The bits in memory are identical. Only the *reading* differs.
160//!
161//! **A tiny 3-bit world.** 256 rows is too many to draw, so pretend numbers had
162//! only 3 bits (8 patterns). Everything below works the same way for 8, 32 or
163//! 64 bits.
164//!
165//! ```text
166//!   bits   unsigned   signed
167//!   000       0          0
168//!   001       1          1
169//!   010       2          2
170//!   011       3          3
171//!   100       4         -4     <- top bit is 1: signed reads it as negative
172//!   101       5         -3
173//!   110       6         -2
174//!   111       7         -1
175//! ```
176//!
177//! **Where the negative numbers come from: place values.** In ordinary binary
178//! each bit is worth a power of two. Signed changes just one thing: **the top
179//! bit is worth minus** its usual value.
180//!
181//! ```text
182//!                 top
183//!   bit worth:    4s   2s   1s
184//!   unsigned:    +4   +2   +1
185//!   signed:      -4   +2   +1      <- only the top bit's sign changes
186//!
187//!   101  unsigned:  4 + 0 + 1 =  5
188//!        signed:   -4 + 0 + 1 = -3
189//!
190//!   111  unsigned:  4 + 2 + 1 =  7
191//!        signed:   -4 + 2 + 1 = -1
192//! ```
193//!
194//! Same for 8 bits, where the top bit is worth −128 instead of +128:
195//!
196//! ```text
197//!   bit worth:   -128  64  32  16   8   4   2   1
198//!   1111_1011:     1    1   1   1   1   0   1   1
199//!                -128 +64 +32 +16  +8      +2  +1  = -5
200//! ```
201//!
202//! That gives a quick shortcut. If the top bit is 0, both readings agree. If
203//! the top bit is 1, it swings from +4 to −4 (a difference of 8, the number of
204//! patterns), so signed = unsigned − 8. For 8-bit types, − 256:
205//!
206//! ```text
207//!   1111_1111 (0xFF):   as u8 = 255   as i8 = 255 - 256 = -1
208//!   1111_1011 (0xFB):   as u8 = 251   as i8 = 251 - 256 = -5
209//!   1000_0000 (0x80):   as u8 = 128   as i8 = 128 - 256 = -128
210//! ```
211//!
212//! (This scheme is called *two's complement*. Every modern CPU uses it.)
213//!
214//! **Think of a circle, not a line.** The patterns sit on a circle like the
215//! numbers on a clock. Adding 1 moves one step clockwise; after the last
216//! pattern you are back at the first:
217//!
218//! ```text
219//!                     000
220//!                    0 / 0
221//!          111                  001
222//!        7 / -1                1 / 1
223//!
224//!      110                          010
225//!     6 / -2                       2 / 2
226//!
227//!          101                  011
228//!        5 / -3                3 / 3
229//!                     100
230//!                   4 / -4
231//!
232//!    (each label is  unsigned / signed;  +1 = one step clockwise)
233//! ```
234//!
235//! Unsigned and signed walk the **same circle**; they only print different
236//! labels. That is why the CPU needs just one "add" instruction for both. It is
237//! also why -1 is all ones (`111`, `0xFF`): it is one step back from zero.
238//!
239//! **The seam: overflow.** Somewhere on the circle the labels jump:
240//!
241//! * unsigned: between 7 and 0 (for `u8`, between 255 and 0)
242//! * signed: between 3 and -4 (for `i8`, between 127 and -128)
243//!
244//! Crossing the seam is called **overflow**: `255_u8 + 1`, `0_u8 - 1`,
245//! `127_i8 + 1`. The bits just keep going round the circle; the only question
246//! is whether you *wanted* that.
247//!
248//! Rust's default: debug builds **panic** when you cross the seam, release builds
249//! silently **wrap** (`127_i8 + 1` → -128). Don't depend on the build mode;
250//! say what you want:
251//!
252//! | Method | `250_u8 + 10` gives | Use when |
253//! |---|---|---|
254//! | `wrapping_add` | `4` | going round the circle is intended (ring counters, hashes, tags) |
255//! | `checked_add` | `None` | overflow is an error you want to handle |
256//! | `saturating_add` | `255` | stop at the edge instead of going round |
257//! | `overflowing_add` | `(4, true)` | you need the result *and* whether it wrapped |
258//!
259//! (In C and C++, crossing the seam with a *signed* type is undefined behaviour:
260//! the compiler may assume it never happens. Rust has no such trap.)
261//!
262//! **Converting with `as`: same bits, new label.** `as` never checks anything.
263//! It only relabels or resizes:
264//!
265//! * **Same size**: keep the bits, read them the other way.
266//!   `-1_i8 as u8` = 255, `200_u8 as i8` = -56 (200 - 256).
267//! * **To a bigger type**: add bits at the top. Unsigned adds 0s, so
268//!   `255_u8 as i32` = 255. Signed adds copies of its top bit, so negatives stay
269//!   negative: `-1_i8 as i32` = -1 (all 32 bits are 1: `0xFFFF_FFFF`).
270//! * **To a smaller type**: chop off the top bits. `300_u32 as u8` = 44, because
271//!   300 = `1_0010_1100` and the low 8 bits `0010_1100` are 44.
272//!
273//! Want a check instead? `u8::try_from(300)` returns an error rather than chopping.
274//!
275//! **Right shift keeps the sign for signed types.** `>>` slides every bit one
276//! place right, which leaves an empty spot at the top. Unsigned fills it with 0.
277//! Signed fills it with a copy of the top bit, so a negative number stays
278//! negative (and it still halves the number):
279//!
280//! ```text
281//!   u8:  1111_1000 (248)  >> 1  =  0111_1100 (124)
282//!   i8:  1111_1000 (-8)   >> 1  =  1111_1100 (-4)
283//! ```
284//!
285//! **Negating by hand** (rarely needed): flip every bit, then add 1.
286//!
287//! ```text
288//!    5  = 0000_0101
289//!   flip  1111_1010
290//!   +1    1111_1011  = -5
291//! ```
292//!
293//! **Two signed surprises.**
294//!
295//! * There is one more negative number than positive: `i8` goes down to -128 but
296//!   only up to +127 (in the 3-bit world: down to -4, up to +3). So -128 has no
297//!   positive partner, and `(-128_i8).abs()` and `-128_i8 / -1` overflow.
298//! * Division rounds toward zero, and `%` keeps the sign of the left number:
299//!   `-7 / 2 = -3` and `-7 % 2 = -1`. For a remainder that is never negative
300//!   (e.g. to use as an array index), use `rem_euclid`: `(-7_i32).rem_euclid(2) = 1`.
301//!
302//! **Why this crate uses unsigned types** (`usize`, `u32`, `u64`): indexes,
303//! counters and bit patterns are never negative. With unsigned types, `&` masks,
304//! `>>` shifts and wrap-around all behave exactly like the pictures above, with
305//! no sign bit to worry about.

312/// Checks the real-Rust-type numbers quoted in the "Unsigned vs signed integers" refresher.
313#[cfg(test)]
314mod refresher_tests {
315    #[test]
316    fn signed_unsigned_examples() {
317        assert_eq!((0xFF_u8 as i8, 0x80_u8 as i8), (-1, -128));
318        assert_eq!(0b1000_0001_u8 as i8, -127);
319        assert_eq!(-5_i8 as u8, 0xFB);
320        assert_eq!(0xFB_u8.wrapping_add(0x07), 0x02);
321        assert_eq!((-1_i8 as u8, 200_u8 as i8), (255, -56));
322        assert_eq!((255_u8 as i32, -1_i8 as i32), (255, -1));
323        assert_eq!(-1_i8 as i32 as u32, 0xFFFF_FFFF);
324        assert_eq!(300_u32 as u8, 44);
325        assert_eq!(300_u32, 0b1_0010_1100);
326        assert!(u8::try_from(300_u32).is_err());
327        assert_eq!(0x80_u8, 128);
328        assert_eq!(!5_i8 + 1, -5);
329        assert_eq!((0xF8_u8 >> 1, -8_i8 >> 1), (0x7C, -4));
330        assert_eq!(127_i8.wrapping_add(1), -128);
331        assert_eq!(250_u8.wrapping_add(10), 4);
332        assert_eq!(250_u8.checked_add(10), None);
333        assert_eq!(250_u8.saturating_add(10), 255);
334        assert_eq!(250_u8.overflowing_add(10), (4, true));
335        assert_eq!((-128_i8).checked_abs(), None);
336        assert_eq!((-128_i8).checked_div(-1), None);
337        assert_eq!((-7 / 2, -7 % 2, (-7_i32).rem_euclid(2)), (-3, -1, 1));
338    }
