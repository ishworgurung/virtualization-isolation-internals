Thin helpers over the cgroup v2 filesystem.

A cgroup (“control group”) is a set of processes that the kernel accounts for and limits as a group: total CPU time, memory, number of tasks, I/O bandwidth. Containers, systemd services and Firecracker microVMs are all confined this way. cgroups do not isolate what a process can see (that is namespaces’ job); they limit what it can consume.

The entire cgroup API is a file tree (normally /sys/fs/cgroup):

  • mkdir a directory -> create a cgroup
  • rmdir it -> destroy it (must be empty of processes)
  • write a PID to cgroup.procs -> move that process in
  • write to memory.max, cpu.max, … -> set limits
  • read memory.current, cpu.stat, *.pressure … -> observe No syscalls beyond open/read/write/mkdir/rmdir — which is why this crate has no dependencies.

Children (threads and forked processes) start in their parent’s cgroup, so placing one process in a group confines everything it later creates.

is_v2
Is this a cgroup v2 (unified hierarchy) host? v2 has a single tree with a cgroup.controllers file at its root; v1 mounts one tree per controller (/sys/fs/cgroup/cpu, /sys/fs/cgroup/memory, …).
