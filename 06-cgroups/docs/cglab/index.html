cglab — a hands-on tour of cgroup v2.

cglab info                      what does this host/cgroup look like?
cglab limits                    cpu.max, memory.high, memory.max (OOM), pids.max
cglab weight                    cpu.weight: proportional sharing under contention
cglab nip                       the "no internal processes" rule
cglab gomaxprocs                what Go >= 1.25 (and Rust std) derive from cpu.max
cglab jail --cpu 50 --mem 64 --pids 32 -- <cmd...>     jailer-style confinement
cglab clean                     remove stale cglab-* groups
cglab all                       info + limits + weight + nip + gomaxprocs

Everything runs unprivileged inside a systemd-delegated subtree (user@UID.service), or anywhere you point CGLAB_ROOT.

How the demos generate load: the binary re-runs itself with a hidden worker subcommand (see worker), started inside a freshly created cgroup via cg::spawn_in. The parent then reads the cgroup’s statistics files to show what the kernel did to the worker.

effective_cpu_limit 🔒
Effective CPU limit implied by cpu.max of this cgroup AND all ancestors (the tightest wins), in CPUs (quota / period). None = unlimited. This is the input Go >= 1.25 starts from when choosing its default GOMAXPROCS (Go then applies its own rounding and minimum).
gomaxprocs 🔒
cglab gomaxprocs: show how a CPU quota translates into “how many threads should my runtime run in parallel”.
